# 3. Software packages and algorithms employed

## 2026-08-29 — ai — four defects in `build_views.py`, and no check mode in `build_codebook.py`

Found while running the pre-coding orientation the coding protocol requires. All five fixes are in this commit; both scripts were tested before the patch was applied.

**`build_views.py` read the wrong vocabularies.** `load()` opened `loss_mitigation_characteristic.csv` and `loss_mitigation_type.csv` regardless of `--dataset`. Every WP2 component of `organizational_forms` exited with "no characteristics with component 'legal-personality'", and `--component owner-shielding` **succeeded silently with nonsense**, crossing organizational form ids with `LS3`/`RB3`/`RB4` and printing a table in which every cell was `--`. That file, `views/organizational_forms--owner-shielding.md`, was generated in error on 2026-08-29 and has been deleted.

**The mechanism filter assumed `MC1`**, which exists only in `loss_mitigation_forms`; against any other dataset it silently matched nothing. Now guarded, and the caption no longer prints `MC1 = None` for a dataset that has no `MC1`.

**The claim table's default assumed `PR1,PY0`.** With the first two defects fixed, every `organizational_forms` view then died with `KeyError: 'PR1'`. **Found only by running the patched script**, which is the argument for testing a patch rather than reading it.

**The TeX claim-table caption hardcoded a substantive assertion** about `PR1` and `PY0` — that ex-ante pricing is a separate axis rather than a stage of mechanism — and printed it above any claim table whatever characteristics it actually showed. A caption stating a finding the table beneath it does not support is a citable error waiting to happen. The assertion is now emitted only when the claim is in fact `PR1,PY0`.

The fix adds a `VOCAB` registry mirroring the one already in `check_dependence.py` — one source of truth, not two — plus `MECHANISM_KEY` and `DEFAULT_CLAIM`, and validates explicitly-passed claim codes against the loaded vocabulary. **Regression: the committed `loss_mitigation_forms` markdown and TeX views regenerate byte-identical to their pre-patch output.**

**Significance beyond the code.** The protocol's orientation step requires generating the comparative view before coding, so that a coding is comparative rather than self-consistent. **That step was unavailable for `organizational_forms` for as long as the dataset has existed**; every organizational-form coding to date was made without it.

**`build_codebook.py` had no check mode.** It took a dataset directory positionally and treated any argument as one, so `--check` failed with `FileNotFoundError: .../--check/datapackage.json`, as did `--help`. Now `argparse`, an optional positional, and `--check` with a non-zero exit on drift. Running it immediately found that `datasets/loss_mitigation_forms/codebook.md` is stale — 563 rows recorded against 740 in `data.csv`, the kō batch having been merged without regenerating. Not fixed here: regenerating it is a data-side commit, not a tooling one.

**Also noted, not fixed.** `views/loss_mitigation_forms--risk-pooling.md` is stale; `build_views.py --check` reports it correctly and exits 1.


## 2026-07-19 — MS

Two normalisation algorithms are in use for gold→silver conversion (ryō→monme, `normalization_method`): `ryo_to_monme@60_official1700`, the pegged official Tokugawa rate, and `ryo_to_monme@61_market_est`, an estimated market rate for periods where the official peg is known to have come under pressure. Where a transaction's rate is contested, both conversions are kept as separate rows (e.g. `CR-0002` vs `CR-0003`) rather than collapsed to one — the discarded alternative stays in the data, flagged with lower `confidence`, so the sensitivity is auditable rather than buried in a footnote.
