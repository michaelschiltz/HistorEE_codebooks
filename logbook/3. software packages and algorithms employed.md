## 2026-09-07 (ii) — ai — building the first real re-coding bundle found three more leak surfaces in the same script, all of them things the earlier fix had trusted; the lesson is that a scrubber is only as good as the audit that reads its output

The morning's patch (2026-09-07, above) was written and tested against throwaway bundles built from the codebooks half alone, because the vault was not reachable from the machine it was written on. **Building the real bundle — both halves, into the real destination — found three further defects within twenty minutes.** None was in the code the patch added. All three were in code the patch had trusted.

**Defect 4: `graph.svg` is not regenerated, and it embeds every note title.** `drop_notes_by_session` runs the vault's `export_graph.py` and reports "regenerated graph/ from the scrubbed note set". The exporter rewrites `graph.dot`, `graph.html` and `graph.json` — and leaves `graph.svg`, a committed Graphviz rendering it does not produce. The SVG in the first real bundle was dated 2 August and carried the titles of both notes the scrubber had just removed. **Every blind bundle built since the graph handling was written has shipped this**, and the script's own comment says a title is a claim. The fix does not reason about which artefacts carry titles: it records `graph/`'s mtimes before the exporter runs and **deletes anything the exporter did not rewrite**, on the ground that an artefact the generator did not touch is stale by definition. Regeneration where possible, deletion where not — the same posture as `rebuild_views`.

**Defect 5: the wikilink dereferencer was line-oriented, and this vault hard-wraps.** `re.sub(rf"\[\[{e}\]\]", ...)` cannot match `[[Harris 2020 on the late plurality of limited\nliability]]`, and one surviving note carried exactly that, so a withheld title stood in a note the coder reads. The title is now matched with `\s+` between its words and an optional `|alias`, in the MOC-line, link-reference and inline branches alike. Thirteen files dereference in the real bundle where five did before.

**Defect 6, and it is the one I would least have predicted: logbook 4's standing spent-blind table is not a dated section, so nothing scrubbed it.** Each of its rows states what a session read and **which cells and characteristics it therefore prejudices** — a description of the batch under test, written by the operator who designed it. The built bundle contained **this session's own row**, naming the five cells, both sources, the jingle rule and the joint-and-separate-estates doctrine, and pointing at the selection brief. New `drop_standing_rows(path, sessions)` removes any table row whose leading `` | `slug` | `` cell matches a withheld session; eight rows go and the table's prose survives. **The slug list now has to include the operator's own slug for the current batch**, which is a discipline the operator must remember and the script cannot infer.

**The audit was extended in consequence, and this is the general point.** `residual_mentions` swept for withheld *type codes* only. A removed note's title survives wherever prose **quotes** it rather than links it, and no dereferencer reaches a quotation — logbook 4 quoted one twice, as evidence of what a session spent. It now sweeps withheld titles as well as type codes, and the manifest says why a quoted title is a leak.

**One of the six was mine, and it is worth recording as a hazard of the genre.** The comment I wrote for defect 5 quoted the real withheld title as its worked example. **This script ships inside the bundle.** A comment in a scrubber that names what the scrubber removes is a leak in the scrubber, and the comment now carries an invented title and says why.

### What this says about the earlier entry

The morning's entry claimed the vault path was "exercised but not exercised against `myfoamrepo`" and asked the operator to read that half of the first manifest with that in mind. **That caveat was correct and it was not enough.** Two of the three defects here are in the vault half and neither would have been found by reading a manifest: one is in a binary-ish generated artefact the manifest never mentions, and the other in a regex that fails only against a wrapping style the test vault did not have. **A synthetic fixture tests the code you wrote; only the real input tests the assumptions you did not know you had made.** The rule this yields for the next patch of this script is to build the real bundle before writing the logbook entry, not after.

**Verification.** Bundle rebuilt from scratch after each fix. Final state: 769 rows and 31 types against 833 and 33 live; `check_vocabularies.py` passes at 164 codes; `check_dependence.py` passes; `build_views.py --check` reports the regenerated views self-consistent with the scrubbed data; the withheld forms appear in no view; and `jingle`, `Getzler`, `Macnair`, `Holdsworth`, `Ex parte Elton` and the withheld note titles return **zero** across both repos. Twenty-two residual mentions remain and are reviewed by hand in the selection brief §7.


## 2026-09-07 — ai — `make_blind_bundle.py` could not blind a RE-CODING: it left the type row and every view standing, and it could not see what survived; three additions, and the audit found a real leak on its first run

`--withhold-types` was written for a **first** coding, where the form has no rows, no type row and no place in any view, and removing its `data.csv` rows and the generated codebooks is the whole job. A **re-coding** is the opposite case — the form is fully coded and the point is to hide what it says — and against that case the option was close to decorative. Found while preparing the `deed_of_settlement_company` shielding re-coding; the bundle that batch needs could not have been built before this commit.

**Defect 1: the vocabulary type row survived, and its `key_source` is where the reasoning under test is written.** This census keeps each form's scope note, source disambiguation, non-independence declarations and co-occurrence bases in `organizational_form_type.csv`, in prose that routinely names cells and says why they read as they do. Shipping it beside a scrubbed `data.csv` hands the coder the argument while withholding only the number. New `drop_csv_rows(path, column, values)` removes whole rows by `code` from every `*_type.csv`, rewriting with `lineterminator="\n"` and `newline=""` because `.gitattributes` requires LF and `csv.writer` defaults to CRLF — the same trap that failed `check_vocabularies.py` on 2026-09-04.

**Defect 2: all nine component views survived, and a view tabulates every coded form on its component.** `views/organizational_forms--entity-shielding.md` states `AP1`, `AP2` and `AP4` for every form in one table, so the withheld values were sitting in a file the coding protocol explicitly tells the coder to read. New `rebuild_views(cb, datasets)` **regenerates** each scrubbed dataset's views from the scrubbed `data.csv` rather than deleting them, because `code-a-form` step 1.3 needs them; deletion is the fallback for any view the generator will not rebuild, and only the scrubbed datasets are touched. Nine regenerated on the test bundle, none deleted.

**Defect 3, and the one that matters most: nothing could see what survived.** Removing a form's own rows is automatable. Removing every **other** row's discussion of it is not — characteristic definitions, neighbouring forms' cell notes and other type rows' scope prose all legitimately name it, and all must survive, because they are what the coder needs. **A re-coding bundle therefore always leaks something, and the only safe posture is to make the leak visible rather than to claim it away.** New `residual_mentions(root, types)` sweeps every surviving `.md`, `.csv`, `.json` and `.txt` file in **both halves** of the bundle for mentions of a withheld type and reports `file:line` with 250 characters of context; the manifest gains a `RESIDUAL MENTIONS — HAND REVIEW REQUIRED` section, and the manifest's `Limits` paragraph now distinguishes a first coding from a re-coding instead of stating the first case as if it were the rule.

**It runs LAST, after every removal, and that ordering was a bug before it was a decision.** The first version ran inside the `--withhold-types` branch, before `CHANGELOG.md` was deleted and before the vault was scrubbed: it reported 39 hits of which twelve were in a file the script deleted three lines later. Reporting a leak in a file that does not ship is worse than not reporting it, because it spends the reviewer's attention on nothing. Moved to the end of `main()`, given the bundle root rather than the codebooks root, and the count on the same inputs fell from 39 to **27 real ones**, now labelled `HistorEE_codebooks/...` and `myfoamrepo/...` rather than bare.

**The vault half needs the sweep as much as the codebooks half.** Vault notes are removed by **session slug**, so a note written by a session the operator did not list can still name the form and state a value. Tested on a synthetic vault holding one note reading "On `deed_of_settlement_company` the `AP1` cell reads 1"; the sweep reports it at `fakevault/notes/n1.md:5`. **The real vault was not reachable from the machine this patch was written on**, so the vault path is exercised but not exercised against `myfoamrepo`; the operator should read that half of the first real manifest with that in mind.

### What the audit found on its first real run, which is the argument for having written it

`datasets/organizational_forms/data.csv:711` — `compagnie_antwerpen_1582 AP2`, coded 2026-09-05 — says of the form under test: *"see … the `deed_of_settlement_company` AP2 note. Both that row and this one read P and the two P's are not the same state, so they are not agreement."* **That states one of the five values the re-coding exists to reach independently**, in a neighbouring form's cell note, in a file that must ship. No amount of type-row and view scrubbing would have caught it, and the batch it would have spoiled is the batch this patch was written for.

Two further hits state values of the same form on characteristics **outside** this batch's five (`FP2=0`, `CF3=multilateral`, `MG1=.NR`) and are left alone: the blind covers the cells under test, not the form's whole row. The eight hits in `organizational_form_characteristic.csv` are the `entity`-locator text and are disclosed to the coder in the prompt rather than removed, because removing them destroys the vocabulary the coder codes from — see the selection brief §6.

**A general lesson, and it is not about this script.** The earlier version of `--withhold-types` was not wrong about anything it did; it was wrong about what it claimed. It reported what it had removed and said nothing about what it had left, and a scrubber that reports only its removals reads as complete. **The fix that mattered was not a third removal but a report of the residue** — the same shape as the `check_dependence.py` path-versus-flag failure of 2026-08-29, where a tool exited 0 while doing nothing.

**Not changed.** The vault scrubber, the date and session removal, `drop_csv_column`, `head_of`, `copy_repo`; no new dependency, standard library and `subprocess` to the existing generators only. The script still has **no `--sources` option** and the operator still copies source PDFs into `sources/` by hand.


## 2026-09-05 — ai — `build_views.py` emitted unpadded Markdown tables while `build_codebook.py` padded them; the views are now padded by the same function

The two generators in `scripts/` disagreed about Markdown tables. `build_codebook.py` has aligned its columns since it was written, through its own `md_table(headers, rows, aligns)`; `build_views.py` wrote `"| form | " + " | ".join(...)` and a bare `"|---" * (n + 1)` separator. Nothing documented the difference and nothing checked it.

**The cost is in the history rather than in an argument.** `views/loss_mitigation_forms--risk-pooling.md` was prettified by hand and committed twice on 2026-09-05 — `tables prettifed`, then `table prettified` — and each time it went stale against its own generator the moment it landed, because the generator would have rewritten it unpadded. Since 2026-08-31 CI rebuilds every `views/*` and runs `git diff --exit-code`, so from that date a prettified view **fails the build on whitespace alone**, with no cell changed and nothing to see in the diff but spaces. That is the worst shape a check can fail in: it is right to fail, and it tells the reader nothing about why.

**The repair is to import the padder, not to write one.** `build_views.py` now does `from build_codebook import md_table`, with `sys.path` nudged to the script's own directory so the import holds however the script is invoked (verified from `/tmp` as well as from the repository root). **A second table renderer was the obvious quick fix and would have been the same mistake this repository had just made elsewhere:** `CONTRIBUTING.md` §4 warns that an unregistered duplicate is precisely what drifts unnoticed, and the `source_lang` enum — duplicated across two datapackages with no agreement check, drifting for three weeks until Turkish sources arrived — had demonstrated it the day before. Two padders in one `scripts/` directory would have drifted the same way and been discovered the same way, by a build failing on something invisible.

**Both Markdown tables go through it:** the scoped matrix and the claim table. The loss-mitigation risk-pooling view emits both, so neither path is untested. **The LaTeX renderer is untouched** — `tabular` alignment is the compiler's business and no prettifier reaches it.

**All ten views regenerated, and the two conventions have converged.** The loss view now reproduces the committed hand-prettified file, so the last of those two commits becomes a no-op rather than a thing to undo. The nine organizational views take the padding as well as this week's new rows. **What this buys is that prettifying is now the generator's job**: running a Markdown table formatter over `views/` is idempotent, and the failure mode that produced two commits and a false diagnosis cannot recur.

**Recorded against my own earlier reading.** On first meeting the padded file I concluded from the absence of any `prettier`, `editorconfig`, `markdownlint` or `pre-commit` config, and of any active hook, that "nothing in the repository does this, so it came from an editor" — and recommended regenerating the file to the generator's unpadded output. The reflog said otherwise: a person did it, deliberately, twice. Absence of tooling is not absence of practice, and the working copy is not the only evidence about a repository.

**Not changed here.** `build_codebook.py` itself, whose output is unaffected; the LaTeX path; the CI workflow, which needed no edit. Standard library only, no new runtime.


## 2026-08-31 — ai — the soft-wrap convention is now a checker, and CI runs it repo-wide

The convention was written into `CLAUDE.md`, `logbook/README.md` and a per-file reminder comment earlier the same day (commit `15a4d41`). Documentation without a check did not hold: `logbook/1`, `3`, `4` and `5` were still hard-wrapped at ~90 columns — 195 paragraphs in all — and would have had to be reflowed by hand again. New file `scripts/check_softwrap.py`; new CI step in `validate.yml`; `markdown-it-py` added to the CI install line.

### The algorithm, and why it is a parser and not a heuristic

`markdown-it-py` tokenises each file; the check flags every `paragraph_open` token whose source span (`token.map`) covers more than one non-blank physical line. One rule catches paragraphs, list items — tight and loose — and blockquote bodies at once, because all three wrap their content in a paragraph token. Headings, tables, thematic breaks, fenced and indented code, and HTML blocks are exempt for free: they are other token types. The table rule is explicitly enabled so pipe tables are not misread as wrapped paragraphs.

The first draft was a line-length/indentation heuristic. It false-positived on 4-space-indented code blocks and on consecutive list items — it reported the already-correct `logbook/6` and `README.md` as violators. Discarded for the token walk, which agrees with the rendered structure by construction.

### `--fix`, and the one judgement it refuses to make

`--fix` joins each offending span into a single line, carrying the first line's indent, or one normalised `>` marker for a blockquote, and stripping wrap markers from the continuation lines. It is rendering-preserving: a token-stream diff of the five reflowed files shows only bare `>` wrap markers removed, no prose word altered.

It does **not** try to re-separate a paragraph that a missing blank line has turned into a list item's lazy continuation — CommonMark has already folded that prose into the bullet, and guessing the split back out is the kind of silent structural decision `CLAUDE.md` forbids. It folds such prose into the bullet and leaves a long line for a human to split. One case survives, at `logbook/1`'s `begijnhof` five-cell bullet.

### Scope

All `*.md` under the repo root except three globs in the script's `EXCLUDE`: the verbatim `LICENSE-DATA.md`, and the generated `datasets/*/codebook.md` and `views/*.md`, whose wrapping would have to change in `build_codebook.py` / `build_views.py` rather than in the file. No `CHANGELOG.md` entry and no `version` bump: no data or schema changed.

## 2026-08-30 — ai — two generators were wrong or unguarded, and a view had been stale for three weeks

Both patches had been sitting in `proposed-of/` since 29 August with a test transcript and were applied today. No coded value changes.

### `build_views.py` could not view `organizational_forms` at all

`load()` opened `vocabularies/loss_mitigation_*.csv` unconditionally, whatever `--dataset` said. Every WP2 component returned "no characteristics with component …", and a WP1 component name silently crossed organizational-form ids with `LS3`/`RB3`/`RB4`. **No view of the organizational matrix has ever been generated by this repo.** The patch adds a `VOCAB` registry mirroring `check_dependence.py`'s, makes `--mechanism` dataset-aware (`MC1` exists only in `loss_mitigation_forms`), and stops the claim table defaulting to `PR1,PY0` against a vocabulary holding neither.

**A methodological point, since this is the tool the component sets are read through.** For six weeks the only buildable views were WP1. The WP2 facets were not being examined because they *could not be*, and the "coverage is currently a property of the bibliography" observation in the 2026-08-29 (iii) entry was made without ever seeing a WP2 view. Whether that shaped which forms were chosen is not answerable from here, but it should be on the record that the instrument was broken while the choices were made.

### Regression testing, and a trap in it

Comparing pre- and post-patch output requires the **old script in a full tree**: `ROOT` is `Path(__file__).resolve().parent.parent`, so a backup copy run from a scratch directory silently resolves to the wrong repository root and dies on a missing vocabulary. A first attempt was invalidated that way. Rebuilt properly, pre- against post-patch across all four WP1 components in both `md` and `tex`: **byte-identical, every one.**

### `build_codebook.py --check`, and where the hole really is

`--check` verifies the committed codebook against the generator without writing; exit 1 on drift or absence, naming the file. Tested for drift detection, the missing-file case, non-mutation, and positional-argument compatibility. `import sys` became dead when `argparse` replaced `sys.argv` and was removed.

**CI already regenerates codebooks and fails on drift**, so this is a local pre-commit convenience rather than new enforcement. **CI does not look at `views/` at all**, and that is the gap that actually bit: `views/loss_mitigation_forms--risk-pooling.tex` was dated 9 August, reported **12 forms against an actual 29**, and was missing the entire kō batch, the guild boxes, the friendly societies, the Edinburgh craft funds and the Italian confraternity fund. Its `.md` sibling was regenerated on 29 August and the `.tex` was left behind. Three weeks, every other check green.

Regenerated; both formats now pass `--check`. The dated `-2026-08-19` `.tex`/`.pdf` pair is deliberately untouched — the committed PDF was built from it, so `views/` now holds one frozen snapshot and one live view rather than three vintages of the same thing.

**A CI step for views is the real fix and was not written.** It would have to parse committed view filenames for their dataset and component, which is a script change rather than a workflow line. Recorded here so it is not lost.

### Also

`codebook.md` goes stale on **data** change, not only schema change, because it publishes row counts and per-field fill counts. It stood at 485 rows against an actual 579 this morning, having missed two batches — the rule as written tied regeneration to schema growth, which is why nobody ran it. `CLAUDE.md` now says so. `.gitignore` gains the LaTeX build artefacts; a `.synctex.gz` had been committed on 19 August.


## 2026-08-29 — ai — four defects in `build_views.py`, and no check mode in `build_codebook.py`

Found while running the pre-coding orientation the coding protocol requires. All five fixes are in this commit; both scripts were tested before the patch was applied.

**`build_views.py` read the wrong vocabularies.** `load()` opened `loss_mitigation_characteristic.csv` and `loss_mitigation_type.csv` regardless of `--dataset`. Every WP2 component of `organizational_forms` exited with "no characteristics with component 'legal-personality'", and `--component owner-shielding` **succeeded silently with nonsense**, crossing organizational form ids with `LS3`/`RB3`/`RB4` and printing a table in which every cell was `--`. That file, `views/organizational_forms--owner-shielding.md`, was generated in error on 2026-08-29 and has been deleted.

**The mechanism filter assumed `MC1`**, which exists only in `loss_mitigation_forms`; against any other dataset it silently matched nothing. Now guarded, and the caption no longer prints `MC1 = None` for a dataset that has no `MC1`.

**The claim table's default assumed `PR1,PY0`.** With the first two defects fixed, every `organizational_forms` view then died with `KeyError: 'PR1'`. **Found only by running the patched script**, which is the argument for testing a patch rather than reading it.

**The TeX claim-table caption hardcoded a substantive assertion** about `PR1` and `PY0` — that ex-ante pricing is a separate axis rather than a stage of mechanism — and printed it above any claim table whatever characteristics it actually showed. A caption stating a finding the table beneath it does not support is a citable error waiting to happen. The assertion is now emitted only when the claim is in fact `PR1,PY0`.

The fix adds a `VOCAB` registry mirroring the one already in `check_dependence.py` — one source of truth, not two — plus `MECHANISM_KEY` and `DEFAULT_CLAIM`, and validates explicitly-passed claim codes against the loaded vocabulary. **Regression: the committed `loss_mitigation_forms` markdown and TeX views regenerate byte-identical to their pre-patch output.**

**Significance beyond the code.** The protocol's orientation step requires generating the comparative view before coding, so that a coding is comparative rather than self-consistent. **That step was unavailable for `organizational_forms` for as long as the dataset has existed**; every organizational-form coding to date was made without it.

**`build_codebook.py` had no check mode.** It took a dataset directory positionally and treated any argument as one, so `--check` failed with `FileNotFoundError: .../--check/datapackage.json`, as did `--help`. Now `argparse`, an optional positional, and `--check` with a non-zero exit on drift. Running it immediately found that `datasets/loss_mitigation_forms/codebook.md` is stale — 563 rows recorded against 740 in `data.csv`, the kō batch having been merged without regenerating. Not fixed here: regenerating it is a data-side commit, not a tooling one.

**Also noted, not fixed.** `views/loss_mitigation_forms--risk-pooling.md` is stale; `build_views.py --check` reports it correctly and exits 1.


## 2026-07-19 — MS

Two normalisation algorithms are in use for gold→silver conversion (ryō→monme, `normalization_method`): `ryo_to_monme@60_official1700`, the pegged official Tokugawa rate, and `ryo_to_monme@61_market_est`, an estimated market rate for periods where the official peg is known to have come under pressure. Where a transaction's rate is contested, both conversions are kept as separate rows (e.g. `CR-0002` vs `CR-0003`) rather than collapsed to one — the discarded alternative stays in the data, flagged with lower `confidence`, so the sensitivity is auditable rather than buried in a footnote.
